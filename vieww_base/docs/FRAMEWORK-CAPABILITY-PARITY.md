# ViewW — exhaustive capability cross-check against `What are the best UI frameworks.md`

**Review basis.** This audit checks the complete supplied comparison document: the executive summary, every framework row and column, narrative capability summaries, maturity timeline, capability diagram, three code examples, and cited use/adoption statements. The source used for ViewW is the available repository archive and code-browser snapshot, not a live checkout of `feature/vieww_code_base`; GitHub could not be fetched from this session. The results therefore describe that snapshot and must be reconciled against the target branch before merge.

**Meaning of “closed”.** A feature is marked *source-present* only when a corresponding implementation is present in the inspected source. *API-slice* means the patch adds a limited building block, not the competitor system's full capability. *Needs verification* means the source is not proof that a platform/device path works. This is not a blanket parity or performance certification.

**Recheck (2026-10-10).** A second pass found one concrete inconsistency missed by the prior review: the particle color test expected Display-P3 space to survive interpolation, while the helper delegated to `Color::lerp`, which deliberately returns sRGB. The implementation and test were corrected together. This recheck was made against the included source archive because the live GitHub branch remained unreachable. No Rust toolchain is installed here, so the correction is source-reviewed but not compiler-verified; that test must still be run before merge.
The same pass also compared the audit's former “no CI workflow” statement with the repository files and found it stale: `.github/workflows/ci.yml` is present. The two available source snapshots do not contain the same workflow: the ZIP archive has manual/tag triggers, while the later code-browser snapshot also runs on pushes to `main` and defines optional self-hosted legs. Both comments explicitly avoid running untrusted pull-request jobs, and the hosted runners do not by themselves certify real-GPU/window or mobile-device behavior. `PENDING.md` now records this snapshot discrepancy instead of treating one workflow version as universally current. The branch URL remains unreachable, so its exact triggers and runner configuration still require confirmation in `feature/vieww_code_base`.

## Executive conclusion

ViewW already has an independent Rust UI model, persistent element/runtime state, widget/layout/render trees, a home-grown CPU rasterizer, a home-grown low-level GPU stack, a Vulkan scene planner, paint paths, text and images, gradients/effects, blend/compositing, animation, gestures, semantics/accessibility hooks, platform bridges, an IDE and test/profiling infrastructure. Replacing these with React, Flutter, Qt, Unity, Skia, wgpu, three.js, a physics dependency, or another framework would violate the stated independence requirement.

The most material feature-class gap exposed by the comparison is 3D/spatial rendering and engine-side primitives. The patch adds `vieww-spatial` as a dependency-free first slice: scene/mesh/material/camera data, CPU triangle rasterization, texture filtering, basic lights, keyframe tracks, simple particles, elementary rigid-body collisions, ray picking, offscreen stereo helpers and a typed expression/behavior-graph evaluator. A second-pass review hardened several entry points and identified/fixed one particle-color test/implementation mismatch; static checks and runtime verification are still incomplete.

**This does not make ViewW feature-identical to Unity, Unreal, Godot, Qt3D, or WebXR.** The patch is a foundational slice rather than the delivery of complete game-engine, authoring, native-GPU, AR/VR, cross-platform or ecosystem parity. No Rust compiler, device toolchain, or real hardware run was available here. It would be false to say all gaps are closed today.

## D. The three code examples

1. **React hover-scale box.** ViewW has pointer/interaction state, widget state and animation primitives. That is not enough to assert exact behavior unless a real example demonstrates enter/exit, pointer capture/cancellation, keyboard/focus equivalence and interruption/reversal. Add an example and behavior test before marking the demonstration closed.
2. **Flutter bouncing ball.** The existing controller/tween/ticker API models timed UI motion, and the new keyed track supplies repeat/ping-pong sampling. The patch does not add a standard integrated `AnimationController` for spatial entities or demonstrate a ball using the spatial renderer at a stable frame cadence.
3. **Unity continuous rotation.** `AnimationTrack<Quat>`/`AnimationTrack<Transform3>` can be sampled at a caller-supplied timestamp. An automatic frame tick, persistent entity, transform update and native-GPU render path are still application/runtime integration work.

## F. Independence and dependency review

The added spatial crate's intended dependency set is only `vieww-foundation` and `vieww-animation`. It uses ViewW's own `Image`, plus standard-library containers/math/time. It does not add `wgpu`, Vello, Skia, three.js, Bevy, a third-party physics engine or a competing UI toolkit. It uses the existing in-house Vulkan components only as surrounding repository infrastructure; this patch does not wire 3D commands into those components.

The lockfile addition should therefore contain only the local `vieww-spatial` package and its two path dependencies. Any unexpected registry dependency in the reconciled branch should block acceptance until explained.

This revision re-read the patch source itself as well as the whole comparison document. The pass covered every file in `crates/vieww-spatial/src/`, the workspace/facade manifests and lockfile changes, the README and `vieww` crate documentation. The following concrete problems in the prior revision were corrected:

| Finding in the prior revision | Correction in this revision | Remaining verification |
|---|---|---|

| A malformed-OBJ test hard-coded a 64-bit `isize::MIN` literal and would fail on 32-bit targets. | The test uses `isize::MIN` from the target architecture. The resolver widens to `i128` before negative-index arithmetic. | Run the test on at least one 32-bit target/toolchain. |

## H. Required acceptance gates (do not waive)

1. Reconcile the patch with the current `feature/vieww_code_base` checkout; verify each patch path and Cargo manifest against that exact branch.
2. Run `cargo fmt --check`, `cargo check -p vieww-spatial`, `cargo test -p vieww-spatial`, facade doctests and the full workspace CI. Static review is not a substitute.
3. Add deterministic image-reference tests for winding/culling, left/right camera orientation, near/far clipping, depth overlap, equal-depth triangles, alpha overlap, UV seams, nearest/bilinear filtering, P3 conversion, normals under nonuniform/negative scale, all light kinds and invalid public-struct values.
4. Add physics fixtures for all collision-pair orderings, coincident centres, static/dynamic inverses, multiple contacts, large timesteps, mutation through `bodies_mut`, overflow and deterministic replay. Do not characterize the simple solver as production physics.
5. Add graph fixtures for missing nodes, all type paths, cycles behind branches, overflow/non-finite values and stable serialization once serialization exists.
6. Integrate the spatial scene into the renderer-independent scene/render graph and resource model before claiming unified UI+3D rendering; implement GPU submission and resource lifetime for each supported backend separately.
7. Add model format fixtures (including concave/non-triangle OBJ faces) and a named supported subset contract. Full glTF, skeletal/skin animation, material assets and morph targets need separate work and compatibility tests.
8. Add actual spatial IDE surfaces (scene graph tree, viewport/gizmo, mesh/material inspector, animation timeline, graph canvas, physics view and asset browser) before claiming Unity/Unreal/Godot-like authoring parity.
9. Add native ARKit, ARCore and WebXR session/input/lifecycle adapters; validate camera permissions, tracking, frame timing and headset/browser presentation on each target.
10. Produce per-target builds and repeated performance runs. Compare matching pixels/workloads/devices with measured p50/p95/p99/p99.9 frame time, CPU/GPU time, memory, startup/cold cache, power, dropped frames and latency. No “faster”, “60fps” or “fully cross-platform” conclusion without the evidence.

## Verdict

This patch adds a meaningful ViewW-owned spatial API and hardens several failure paths. It does **not** honestly satisfy a literal demand for complete parity with every capability named across fifteen UI frameworks and complete game engines. It also does not close the pre-existing `PENDING.md` items. The rows above account for each framework and capability column in the supplied document, and state why a gap is source-present, an API-only slice, irrelevant metadata, or external validation. Anything marked partial/unverified remains open until implemented and tested on the actual branch and target platform.
