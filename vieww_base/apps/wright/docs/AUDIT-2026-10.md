# A deep investigation of Wright, and what 1.0.0 did about it

Date: 2026-10-22 · Against: wright 0.5.2 (~27.7k lines, 7 crates) → this
release, 1.0.0 · By: the rebuild session (see the changelog for the release
contents; this document is the investigation that ordered them)

This is the report the work was ordered against: a deep read of the whole
product — what it does, what the UI-UX promises, where the quality holds and
where it is thin, what the performance profile is — and then the roadmap the
strategy memo ("Making Wright matter: beyond the coding agents") set out,
executed in order. Everything claimed here was either verified on this
machine or is marked as not done.

---

## 1. What Wright is, precisely

Wright is an agent harness where the user never writes code: a person
describes an outcome, an Interviewer drafts a typed blueprint (`blueprint.kdl`,
a KDL dialect), the Confirm Gate renders that blueprint into plain words —
generated by code, never by a model — and nothing runs until the person
approves. A firing then compiles the blueprint into a task graph, stages it by
dependency depth, runs each model-backed agent through a permission gate (every
tool call needs an unforgeable `Permit`), checks the work (Testwright writes
and runs tests; Reviewer approves or rejects), writes a durable event log and
a receipt, and only then delivers. Content-addressed caching means a later
edit re-runs only what it affects; schedules make it run unattended.

The architectural spine, and why the memo's items fit it so well:

| Piece | What it is | Where |
|---|---|---|
| Typed blueprint | KDL dialect → model → validate → canonical form → structural diff | `wright-core` |
| Compiler | blueprint → staged `TaskGraph` with per-task permissions, budgets, tool allowlists | `wright-core` |
| Permission gate | allowlist → capabilities → budget → approval, per call | `wright-runtime` |
| Sandbox | Landlock + netns on Linux; fails closed | `wright-tools` |
| Engine | firing, agent loop, cache, spine, receipts, resume, mock provider | `wright-engine` |
| Store | fsynced event logs, BLAKE3 objects, blueprint history, approvals, spend | `wright-runtime` |
| Built-in models | Qwen3-1.7B + Whisper base, in-process, checked against llama.cpp/whisper.cpp | `wright-infer` |
| The window | vieww shell: Home, sessions, live engine, settings, voice | `wright` (app) |

Doctrine: std-only Rust, one external dependency (vieww), no unsafe outside
three audited files. That doctrine is the moat the memo leans on ("footprint:
one binary"), and every new feature in 1.0.0 had to pass it: the crypto is
reference ports, the MCP client speaks JSON-RPC over stdio with std alone, the
worker tool is a copy + a diff + a subprocess.

## 2. UI-UX: what the product feels like

The window is a pager of full-screen sessions: Home asks "What should exist?",
swiping sideways moves between sessions, pinching shows the overview, the
Confirm Gate is a card of plain sentences before anything runs, the engine
view streams events during a firing. Voice existed inside a session's
composer (capture via vieww's audio backends → the runtime's pure half →
built-in Whisper), and 0.5.2 added live reply streams and kept conversations.

Gaps the investigation found (and what 1.0.0 did):

- **The first touch was typing.** Home's composer had a small mic icon, but
  the page led with a keyboard. The memo's item 6 ("voice first") is now real:
  a big speak affordance above the composer, and a transcript *starts* the
  interview by itself (typing still needs send — a keyboard is a decision
  already made). Pinned by a headless UI test that drives the same inbox path
  the mic worker takes.
- **After a run, the receipt was a JSON file.** `wright explain` now renders
  the one-screen story (plan, what ran, what it sent, what it made, verdict
  per promise, the numbers) from the store — the memo's item 5, and the
  daemon's default view.
- **"What will this cost?" was a guardrail, not a sentence.** `wright run`
  now shows the estimate first and offers the built-in model as choice 2.
- **The trust story had no words on Home.** The Confirm Gate now names the
  Rule of Two legs, untracked artifacts, typed-edge promises and numbered
  acceptance sentences, all generated from the blueprint.

## 3. Quality: where 0.5.2 held, and where it was thin

Held: the layering rule is real (core depends on nothing); the JSON value type
is insertion-ordered (which this release turned into a signing property);
receipts recorded event-log hashes; the sandbox fails closed; the cache has
freshness rules (live data and deliveries are never served from cache); the
tests are written like specs ("a denial is free").

Thin — each became a feature:

1. **Receipts asserted, but did not prove.** Anyone could edit one after the
   fact. → Ed25519 reference port (core), signed `wright.run-receipt/2` with
   inputs' hashes, acceptance verdicts and Rule-of-Two names, and
   `wright verify` with five worded checks (ADR-025).
2. **"Done" was a prose check-line.** The Reviewer read the same sentence the
   person did, but nothing forced the check. → Acceptance sentences the engine
   enforces (ADR-025).
3. **The risky combination was undetectable.** An agent that read your files
   and could fetch and POST existed in a grey zone. → The Rule of Two, typed
   on the palette and enforced twice (ADR-024).
4. **Hand-offs broke silently, two agents later.** → Typed edges, checked at
   plan and fire time (ADR-027).
5. **The ecosystem was closed.** The strongest coding hands (Claude Code,
   Codex, Kimi Code, ZCode) could not be used without abandoning Wright's
   contract. → Workers (ADR-026) and MCP behind permits (ADR-029): Wright
   becomes the manager of agents.
6. **Distribution was `wright new` from scratch.** → The signed recipe gallery
   (ADR-028), with the refusal an unsigned recipe gets.
7. **No public numbers.** → `wright bench` (ADR-030).

## 4. Performance

The product's costs are model tokens and wall time; the harness itself is
negligible (the baseline fires a 6-task graph through the mock in well under a
second; SHA-512 hashes a MB in ~2ms; Ed25519 signs in ~10ms on this container
— rare, once per firing). The built-in models are a fallback and say so, per
ADR doctrine and the memo's "do not oversell" rule. The 1.7B draft quality and
SIMD kernels (the memo's bet #7) remain out of scope for this release and
should stay sequenced after the trust work, exactly as the memo ranked them.
The benchmark harness now exists to measure any of this honestly.

## 5. What was deliberately NOT done, and why

- **Native TLS and sandbox on macOS/Windows (memo bet #5).** The sandbox and
  TLS stories are Linux-complete and fail closed elsewhere; porting Seatbelt /
  AppContainer / OS TLS FFI cannot be built or tested from a Linux-only
  machine, and faking it would be worse than refusing. The new tools follow
  the existing doctrine: they say what they can and cannot do per platform.
- **SIMD kernels / a 4B model (bet #7).** Large, unsafe-heavy, and ranked
  "later" in the memo's own impact/effort chart. The benchmark harness is the
  precondition for that work, and it now exists.
- **A hosted/curated published gallery with real publisher keys.** The
  signing machinery, the install refusal and the gallery sources are in;
  pinning a publisher's key is a distribution decision, not a code one.
- **The 1.0 gate ("10 recipes reach a checked outcome, no key, three
  platforms").** Two of its three legs (native platform coverage, real
  no-key model runs) cannot be satisfied on this machine. The gate stands
  as the definition of done for the 1.0 release; the harness that will
  measure it is in place.

## 6. The verification record

On this machine (kernel 5.10 — *no Landlock*; the sandbox needs 5.13+):

- **Baseline before any change:** 222 unit tests green; the sandbox-dependent
  suites fail closed, exactly as designed, and pass on 5.13+ CI.
- **After the release work (full `cargo test --workspace`):** every new
  module green — core 128 (from 96: SHA-512's OpenSSL/FIPS vectors,
  Ed25519's RFC 8032 §7.1 vectors + three OpenSSL-generated pairs
  byte-for-byte, the Rule of Two's legs/taint/violations, the five edge
  shapes, the recipe round-trip and tamper cases, the Confirm Gate's new
  plain words), runtime 71 (key provenance, gate legs, workers/MCP config),
  tools 29 (worker copy/diff/scope/timeout, MCP pin/allowlist/handshake
  against a stub server), engine lib 20 (verify's checks, bench's honest
  medians, cost's sentences, handoff's folder), plus
  **`engine/tests/trust.rs` — five end-to-end runs through the real engine
  and the mock provider over real HTTP**: a checked outcome that signs its
  receipt and verifies (and fails after one edited byte), a broken typed
  hand-off stopping the plan, a worker step applied whole, the Rule of Two
  refusing a three-leg plan, and every receipt staying verifiable in the
  store. The UI suite runs the real shell headlessly — 8/8 with the new
  voice-first test.
- **The same 12 sandbox failures as the baseline** — the environment's
  kernel, not the code; they are the sandbox doing its job.
- `cargo clippy --workspace --all-targets`: clean on everything new.

## 7. The honest summary

0.5.2 was a well-built harness missing its reason to be trusted. 1.0.0 makes
trust the product: plans that are refused before they run when they hold the
risky combination, runs that end in receipts a third party can check, promises
a person approves and a machine enforces, the strongest external agents inside
Wright's gate instead of outside it, and — where the memo said the real moat
lies — nothing that can be quietly poisoned: signed receipts, signed recipes,
hash-pinned servers. What remains (native platforms, faster local models, the
published gallery) is sequenced, not forgotten, and each has its measure in
place.


## Follow-up implementation — Windows POSIX command sandbox

The audit above records the state at the time it was run. The follow-up patch
adds a Windows backend in `tools/src/sandbox_windows.rs`: POSIX shell, Git and
test commands are invoked inside WSL 2 + Bubblewrap, with a project-only
writable mount, scrubbed environment, no network unless permitted, private
scratch space, output caps, and process/file-size limits. The backend probes
namespace support and refuses to run when its isolation requirements are not
met. Native Windows worker CLIs remain on the existing throwaway-copy boundary
and are explicitly reported as not OS-sandboxed; macOS continues to fail closed.

**Verification status:** this backend was source-reviewed from the Linux
container but could not be compiled or exercised on Windows in that
container. Treat Windows runtime support as implementation-complete but not
release-verified until the Windows CI/device run checks `wright doctor`, a
sandboxed read/write-in-project command, a denied outside-path write, network
permission behavior, timeout cleanup, and paths containing spaces. No claim of
Windows test pass is made by this patch.
